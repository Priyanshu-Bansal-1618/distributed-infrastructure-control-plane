1. Product definition
1.1 Problem statement
A distributed application commonly runs multiple services across multiple machines and replicas. The infrastructure must know which machines participate in a cluster, which services are running on each machine, whether those services are healthy, and where new requests should be sent. Machines and services can join, leave, crash, become unreachable, recover, or temporarily disagree about cluster state.
The system must provide decentralized cluster membership and failure detection, service registration and discovery, service health monitoring, health-aware request routing, configuration distribution, and operational visibility. It must continue operating through ordinary node and service failures and reconcile state after temporary network disconnections.
1.2 Proposed solution
Build a distributed infrastructure control plane composed of independent Node Agent processes. Each agent maintains local cluster state and exchanges membership and service-state updates with peers using a SWIM-inspired gossip protocol. Each agent also exposes an authenticated internal management interface, persists its local state, monitors registered services, and exports metrics.
A separate HTTP reverse proxy/load balancer forms the data plane. It consumes versioned snapshots of healthy service endpoints from the control plane and routes application requests without performing gossip or distributed registry lookups on the request path. A Python management API provides administrative and read-only operations. Prometheus and Grafana provide metrics and dashboards.
1.3 Scope and non-goals
In scope: multi-node cluster membership, gossip dissemination, failure detection, service registry, leases/expiry, health checks, HTTP reverse proxy, routing strategies, configuration versioning/propagation, management API, persistence, observability, fault simulation, tests and Docker-based deployment.
Not in scope for the initial release: full Kubernetes replacement, consensus-backed linearizable registry, general-purpose VPN, custom TCP/IP stack, production-grade global service mesh, automatic cloud provisioning, or a claim of production readiness.
The initial system is eventually consistent for membership, service registry and distributed configuration. Strong consistency must not be claimed unless a consensus/coordination protocol is separately designed and implemented.

2.2 Control plane and data plane
Control plane: maintains desired and observed infrastructure information. It handles node membership, service registration, health state, configuration, and generation of routing snapshots.
Data plane: handles application requests. The load balancer selects a backend from its latest valid routing snapshot and proxies the request. It must not contact the distributed registry synchronously for every request.
The control plane and data plane must communicate through an explicit, versioned interface. A routing update should be validated and applied atomically as a new immutable backend snapshot. Existing requests should be allowed to finish where possible; removed backends should stop receiving new requests and support graceful connection draining.

4. Node Agent specification
4.1 Node identity and record
Each agent has a stable configured node_id and a unique process/boot identity. The node record contains node_id, hostname, advertised address, bind address, gossip_port, sync_port, management_port, incarnation number, lifecycle status, metadata, protocol version and update/version information.
NodeRecord {
  node_id: string
  boot_id: string
  hostname: string
  advertised_address: string
  gossip_port: uint16
  sync_port: uint16
  management_port: uint16
  incarnation: uint64
  status: ALIVE | SUSPECT | DEAD | LEFT
  metadata: map<string, string>
  record_version: uint64
}
Incarnation numbers allow a live node to refute an older suspicion/failure assertion. Do not rely on wall-clock timestamps as the sole conflict-resolution mechanism; clocks can differ.
4.2 Lifecycle
STARTING -> JOINING -> ALIVE -> SUSPECT -> DEAD
                    \-> LEFT (graceful departure)
A restarted process must safely rejoin using its configured identity and
a new boot identity/incarnation policy. Define this policy explicitly.
A graceful departure is different from an unexpected crash. A missed heartbeat is evidence of possible failure, not proof that a machine is dead.

5. Gossip and membership protocol
5.1 Protocol behavior
Implement a SWIM-inspired membership protocol. Keep failure detection and dissemination as separate concerns. Each node periodically selects a peer for a direct probe. If the peer does not respond within the configured timeout, the probing node asks a configurable number of intermediary peers to probe the target. If no indirect probe succeeds, the target is marked SUSPECT and that update is disseminated. If the target does not refute suspicion within the suspicion timeout, it may be marked DEAD.
A suspected node can refute the suspicion by incrementing its incarnation and disseminating a valid ALIVE update. Implement deterministic update validation and precedence. Higher valid incarnation values must supersede older assertions. Define equal-incarnation status handling carefully, including the rules for refutation and terminal states; do not use an arbitrary timestamp last-write-wins rule.
5.2 Probe message flow
Direct probe:
  A -> B : PING(probe_id)
  B -> A : ACK(probe_id)
Indirect probe after direct timeout:
  A -> C : PING_REQ(target=B, probe_id)
  C -> B : PING(probe_id)
  B -> C : ACK(probe_id)
  C -> A : ACK_RELAY(probe_id)
If all probes fail:
  A marks B SUSPECT and disseminates the update.
  If suspicion expires without valid refutation, B becomes DEAD.
5.3 Gossip dissemination
Periodically select peers and exchange bounded batches of membership/service updates.
Support duplicate-message suppression using message identifiers or version tracking.
Use push/pull summaries so a node can request updates it is missing after reconnecting.
Bound message size, queue length and retransmission work. Prioritize important membership transitions.
Handle UDP loss, duplication and reordering at the application layer.
Document convergence assumptions: eventual connectivity, recurring exchanges, and sufficient time for dissemination.

6. Distributed service registry
6.1 Service instance data model
ServiceInstance {
  instance_id: string
  service_name: string
  owner_node_id: string
  address: string
  port: uint16
  protocol: HTTP | HTTPS
  service_version: string
  metadata: map<string, string>
  health: UNKNOWN | HEALTHY | UNHEALTHY | DRAINING
  owner_incarnation: uint64
  record_version: uint64
  lease_expiry: logical/monotonic lease state
}
A service instance is distinct from a node. One node may host multiple instances and multiple services. Node failure must not be confused with an individual service failure.
6.2 Registration and discovery
A service registers with its local Node Agent, providing service name, unique instance ID, listening address/port, protocol, version and metadata.
The agent validates the request, records ownership and version, and disseminates the registration to peers.
Discovery returns eligible instances for a requested service. Normal routing queries must exclude expired, unhealthy, draining or otherwise ineligible instances.
Support explicit deregistration and lease renewal. A service that disappears without deregistering must eventually expire.
Provide deterministic record ordering and conflict resolution per instance. Use owner incarnation plus monotonically increasing record version or another explicitly documented scheme.
Use tombstones for deregistration/deletion and retain them long enough to prevent stale records from reappearing during normal synchronization. Define tombstone garbage-collection rules.
6.3 Consistency model
The initial registry is eventually consistent. Different nodes may temporarily return different results. It does not provide linearizable reads or transactions across the cluster. Document behavior during partitions and after healing. Ensure that stale data cannot remain eligible indefinitely due to missing lease renewal or missed deregistration.
7. Health monitoring
Track node health and service health separately. Node health is inferred from membership probes. Service health is determined by checks against a registered application instance.
Check/state
Definition
Liveness
Whether the service process responds to its liveness endpoint.
Readiness
Whether the service is ready to accept normal traffic.
Active check
Agent periodically sends an HTTP request to a configured health endpoint.
Passive signal (optional)
Proxy observations such as connection failures and upstream errors; must not alone cause unsafe rapid flapping.
Track last success, last failure, response status, latency, consecutive failures and consecutive successes. Use configurable failure and recovery thresholds with hysteresis. Example development defaults: three consecutive failures to mark unhealthy and two consecutive successes to recover.
Health states: UNKNOWN, HEALTHY, UNHEALTHY, RECOVERING, DRAINING. Only healthy and ready instances are eligible for ordinary routing. A node can remain ALIVE while one of its services is UNHEALTHY.
7.1 Circuit breaker
Implement a circuit breaker in the proxy as an optional resilience feature. CLOSED permits normal requests; OPEN stops sending requests to a failing backend; HALF_OPEN permits a limited number of trial requests. Define thresholds, cooldown and success criteria. Keep circuit-breaker state distinct from registry membership and health-check state.
8. HTTP load balancer / data plane
8.1 Request flow
Client
  -> HTTP listener
  -> parse and validate request
  -> identify target service (configured route/path/host mapping)
  -> read current immutable backend snapshot
  -> filter eligible backends
  -> choose backend using configured strategy
  -> proxy request and response
  -> update request/connection metrics
The proxy must support HTTP/1.1 request/response forwarding for the initial release. Define supported methods, headers, body limits, timeout behavior, connection reuse policy and streaming behavior. Correctly handle hop-by-hop headers. Do not claim full HTTP proxy compatibility unless tested.
8.2 Routing strategies
Strategy
Required behavior
Round Robin
Cycle through eligible backends; thread-safe selection.
Weighted Round Robin
Distribute selections according to configured positive weights.
Least Connections
Choose the eligible backend with the lowest active connection count; update counts safely.
Consistent Hashing
Hash a configured request key (e.g. customer ID) onto a ring with virtual nodes; minimize remapping when backends change.
Every strategy must exclude unhealthy, expired, draining and administratively disabled backends. Define deterministic behavior for an empty backend set and return an appropriate gateway/service-unavailable response.
8.3 Dynamic backend snapshots
The control plane generates a versioned list of eligible backend endpoints.
The proxy validates the new snapshot and atomically publishes it for request threads.
Request handling reads a stable snapshot without holding a global lock for the duration of proxying.
When a backend is removed, stop assigning new requests to it and support graceful draining of in-flight connections.
Record snapshot version and update timestamp for diagnostics.
8.4 Proxy metrics
Total requests, successful requests and failed requests.
Requests per backend and selected strategy.
Active connections per backend.
Upstream connection errors and timeouts.
Request latency histogram, including P50/P95/P99 calculated from appropriate histogram data.
Backend snapshot version and update propagation delay.
9. Distributed configuration management
Support versioned configuration records scoped to cluster, service or node. A record includes config_id/key, value, scope, target, version, owner/author, validation status and update metadata. Updates are validated before propagation. Nodes apply only valid, newer versions according to a documented conflict policy.
Provide read, create, update and history operations.
Retain previous values and support rollback as a new version rather than silently rewriting history.
Propagate updates through the control-plane dissemination mechanism or reliable synchronization channel as appropriate.
Provide acknowledgements/observed versions so operators can see which nodes have applied a change.
Support staged rollout: validate, apply to a subset, check health, continue or roll back.
The initial model is eventually consistent. Do not claim atomic all-node updates. Critical changes must document partial-application behavior.

13. Security requirements
Validate every inbound message and API request; enforce maximum message/body sizes.
Authenticate and authorize management operations. Restrict privileged endpoints.
Do not execute arbitrary commands received over the network.
Protect secrets using environment variables or a documented secret mechanism; never commit secrets.
Add rate limits and timeouts to exposed endpoints.
For the advanced security stage, implement mutual TLS for TCP/HTTP agent communication and authenticated UDP gossip messages. HTTPS on the management API alone does not secure UDP gossip.
Define replay protection and message authentication for cluster messages. Document certificate provisioning and rotation if mTLS is implemented.
14. Fault injection and test environment
Provide a reproducible cluster simulator using Docker Compose and scripts. It must support starting/stopping nodes and demo services, introducing latency and packet loss, creating network partitions, restarting nodes and generating HTTP traffic.
Fault
Injection method / expected test
Node crash
Stop an agent container/process; peers should suspect and eventually mark it dead.
Graceful leave
Request drain/leave; peers should receive a departure update.
Packet loss
Use isolated Linux network namespaces and tc netem; measure false suspicion and convergence.
Latency
Inject delay/jitter; observe probe and health-check behavior.
Network partition
Separate node groups; observe divergent local views and reconciliation after healing.
Service crash
Stop one backend while its node remains alive; only that service instance becomes ineligible.
Slow backend
Delay responses; evaluate health policy and circuit breaker.
Node restart
Restart an agent with persisted state; verify identity/incarnation and reconciliation behavior.
Fault injection must be limited to the test environment. Provide cleanup commands that remove network emulation rules and stop containers.
15. Benchmark and evaluation plan
Build repeatable benchmarks and record hardware, OS/kernel, compiler/build mode, node count, network topology, configuration, workload, run duration and repetitions. Report measured results only; never fabricate benchmark figures.
Experiment
Measurements
Cluster convergence
Time for a newly introduced membership update to reach all reachable nodes; repeat at 5, 10, 25, 50 and 100 nodes where feasible.
Failure detection
Time from process termination to SUSPECT and DEAD; false suspicion rate under latency/loss.
Gossip overhead
Messages/bytes per node per second, CPU and memory.
Registry propagation
Time for registration/deregistration to become visible across reachable nodes; stale-record behavior.
Load balancing
Requests/sec, error rate, P50/P95/P99 latency and distribution across backends for each strategy.
Backend failure
Requests sent to failed backend after failure, time to stop routing, failed request count and recovery time.
Recovery
Time for a restarted node/service to rejoin, synchronize and become eligible.
Use wrk or an equivalent HTTP load generator, iperf3 for network baselines, tc netem for network impairment, Linux perf for profiling and Google Benchmark for isolated C++ components.

18. Implementation phases and acceptance criteria
Phase 0 — Architecture and contracts
Inspect repository; produce architecture, module boundaries, ADRs, protocol schemas, configuration schema, API contracts and build plan. Resolve ambiguities before coding.
Phase 1 — Node Agent foundation
Build a C++20 agent with configuration, identity, logging, graceful shutdown, UDP/TCP transport and message serialization. Acceptance: two agents exchange valid structured messages; malformed/oversized messages are rejected; clean shutdown works.
Phase 2 — Membership and gossip
Implement peer bootstrap, direct/indirect probes, suspicion, incarnation refutation, dissemination and push/pull sync. Acceptance: five agents discover one another, detect a killed node, and reconcile after restart.
Phase 3 — Service registry
Implement register, renew, deregister, leases, versions, replication, tombstones and discovery. Acceptance: register on one node and discover from another; stop/expire an instance; ensure stale data does not remain routable indefinitely.
Phase 4 — Health monitoring
Implement active checks, readiness/liveness semantics, thresholds and recovery. Acceptance: a failed service becomes unhealthy while its node remains alive; it becomes healthy after recovery checks.
Phase 5 — Load balancer
Implement HTTP proxy, backend snapshots, four routing strategies, health filtering, metrics and draining. Acceptance: requests reach registered backends; distribution is measurable; failed backends stop receiving new requests.
Phase 6 — Configuration management
Implement scoped versioned config, validation, replication, per-node acknowledgements/history and rollback. Acceptance: updates propagate; stale versions are rejected; rollback creates a new version.
Phase 7 — Management and observability
Implement FastAPI endpoints, authentication, Prometheus metrics and Grafana dashboards. Acceptance: inspect cluster/services/health and observe metrics during a failure test.
Phase 8 — Fault simulation and benchmarks
Implement repeatable node/service failure, packet loss, latency and partition tests; produce benchmark scripts and reports. Acceptance: experiments are reproducible and report measured results.
Phase 9 — Hardening and release
Review security, resource limits, restart behavior, documentation, CI and Docker Compose. Acceptance: fresh checkout builds and runs the documented demonstration without manual code edits.
19. Testing requirements
Unit tests for serialization, message validation, membership update ordering, incarnation/refutation, registry versioning, lease expiration, routing algorithms, circuit breaker and configuration conflict handling.
Integration tests with multiple real agent processes, not only mocked objects.
Deterministic tests using an injectable clock/timer abstraction for timeout and lease logic.
Network tests for packet loss, duplication, reordering, latency and partition/recovery.
Load tests for concurrent HTTP requests, backend failures and snapshot updates.
Stress tests for bounded queues, memory use and shutdown under load.
CI must build in a clean environment and run unit tests on every change. Integration/fault tests may run in a separate CI job if they require privileged networking.
20. Definition of done
The project is complete only when all of the following are true:
Multiple Node Agents run as independent processes/containers and discover one another.
Membership updates disseminate and converge after temporary communication failures.
Direct and indirect probes, suspicion, refutation and failure declaration are implemented and tested.
Services can register, renew, deregister, expire and be discovered across nodes.
Node health and service health are represented independently.
The load balancer routes HTTP traffic using all four documented strategies.
Unhealthy, expired and draining instances are excluded from new routing decisions.
Routing snapshots update safely without a distributed lookup on each request.
Configuration is versioned, validated, propagated and auditable, with rollback.
Local state survives agent restart according to documented persistence rules.
Management API is secured and exposes documented operations.
Prometheus metrics and Grafana dashboards show cluster, gossip, health and proxy behavior.
Docker Compose starts a reproducible demo cluster.
Fault injection demonstrates node crash, service crash, packet loss, partition and recovery.
Automated tests and measured benchmark reports are included.
README and architecture/protocol documentation explain setup, operation, limitations and known issues.

Appendix B — Design constraints to preserve
Membership, registry and configuration are eventually consistent in the initial design.
A node being alive does not imply every service on it is healthy.
The management API is not the cluster's source of truth.
The load balancer uses local versioned snapshots and does not synchronously query the distributed registry per request.
UDP is lossy; application-level message validation, duplicate handling and reconciliation are mandatory.
SQLite is per-node persistence, not shared cluster storage.
A node failure detector can suspect a healthy but unreachable node; document this limitation.
A service lease/expiry and tombstone policy is required to prevent stale registrations from persisting or reappearing.
A working, tested implementation is more important than matching the proposed file count or adding optional technologies.
